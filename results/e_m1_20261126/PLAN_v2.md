# 계획 v2: E-M1 — FnCTOD 추출 + M1 검증 (유료, 승인 요청용)

- 작성: 2026-11-26 밤
- **이 판이 `PLAN.md`(v1, 미승인)를 대체한다.** v1은 지우지 않았다.
- **상태: 승인 대기. 유료 호출은 0회다.** 무과금 dry-run(네트워크 없음)과 가짜 모델 시험만 했다.

## 0. v1에서 바뀐 것

- 추출기를 실제로 구현했다(`cdv/extract.py`).
  - FnCTOD(Li et al., ACL 2024)를 구매 도메인에 적용했다.
  - 공식 코드(`facebookresearch/FnCTOD`, 연구자 포크 `A0-J/FnCTOD` @`243fa2f`, 수정 없음)는 CC BY-NC 4.0이라 복사하지 않았다. 논문에 적힌 방법을 직접 구현했다: 도메인 = 함수, 2단계(함수 선택 → 인자 생성), 이전 턴 함수 호출 포함, 누적 상태.
  - 원본과 다른 점: 구매 도메인 스키마는 직접 작성했다. 선택 단계에서 함수를 여러 개 고를 수 있다. 예시 없는 제로샷이다.
- 비교군을 연구자 지시대로 네 개로 고정했다. 모두 같은 모델을 쓰고, FnCTOD 세 팔은 같은 추출 결과를 쓴다.
- NLI 모델: `MoritzLaurer/DeBERTa-v3-base-mnli-fever-anli`(확정). 근거 찾기(anchoring)와 자유 문장 근거 확인에만 쓴다.
- 요약 판정(SGP 재구현)과 EAL 재구현은 이번 핵심 실험에서 뺀다. 연구자 지시: 핵심 비교 우선.
- gpt-6.1-sol 민감도 실행도 뺀다.

## 1. 비교군 (독립변수)

| 팔 | 내용 | 정답 사용 |
|---|---|---|
| plain | 일반 LLM 추출: 대화 전체를 한 번 읽고 JSON 조건을 낸다. 검증 없이 mandate로 쓴다 | 없음 |
| fnctod | FnCTOD 추출: 사용자 턴마다 2단계 함수 호출. 검증 없이 mandate로 쓴다 | 없음 |
| fnctod_r | FnCTOD + M1 규칙 검증. FnCTOD는 근거를 인용하지 않으므로 M1이 사용자 발화 전체에서 근거를 찾는다(규칙). V-C 비대칭, V-P, V-X, V-S, 누락 검사를 한다 | 없음 |
| fnctod_rn | fnctod_r + NLI. 규칙이 근거를 못 찾은 변경과 자유 문장 항목의 근거만 NLI로 확인한다. 정당성 판정에는 NLI를 쓰지 않는다 | 없음 |
| U(상한, 따로 보고) | 숨은 사양으로 만든 정답 장부 → 같은 결제 검사 | **정답** |

- 결제 검사(M2a, `cdv/pipeline.cart_check`)는 모든 팔에 같다. 기록된 최종 장바구니를 장부와 대조한다: 예산, 수량, 묶음 품목 수, 브랜드.

## 3. 종속변수

| 지표 | 정의(실제 세트) |
|---|---|
| 부당 조건 탐지율 | 추출기가 낸 조건 중 정답 사양과 어긋나는 것(값 불일치, 사양에 없는 조건 — 근거 없는 대체 허용 포함) 가운데, 해당 팔이 장부에 넣지 않은 비율. plain·fnctod는 검증이 없으므로 0 |
| 정상 조건 허용률 | 추출기가 낸 조건 중 정답과 맞는 것 가운데 장부에 들어간 비율 |
| 조건 누락률(조용한 누락) | stated 정답 조건 중 최종 장부에 없고, 경보(CLARIFY)도 없는 비율 |
| 재확인 요청률 | 여정 중 CLARIFY 비율 |
| 정상 거래 오차단율 | 결과 RIGHT 계열 장바구니를 ALLOW하지 않은 비율 |
| 위반 거래 통과율 | 결과 WRONG 계열 장바구니를 ALLOW한 비율 |
| 지연 | 추출(API) 시간, 검증 시간(규칙 / NLI 포함) |

- G1: 템플릿별 정답 상태 일치율(`eval/e_m1/run.py`의 `g1_expect`)

## 4. 가설과 반증

- **H1:** fnctod_r·fnctod_rn의 부당 조건 탐지율이 fnctod(0)보다 높다.
- **H2:** fnctod_rn의 정상 조건 허용률이 fnctod_r보다 높다. NLI가 바꿔 말한 진술의 근거를 찾는다.
- **H3:** 검증 팔의 조용한 누락률이 fnctod보다 낮다(누락 검사).
- **H4(비용):** 검증 팔의 정상 거래 오차단율·재확인 요청률이 오르는 정도를 보고한다. 기준을 미리 정하지 않고 그대로 보고한다.
- 결과가 가설과 달라도 고치거나 빼지 않는다.

## 5. 모델과 비용

- 모델: **gpt-6-luna**(OpenAI Responses API, reasoning effort low, `max_output_tokens` 2,000). 모든 팔과 세트에 같다.
- 단가: 입력 $0.10 / 출력 $0.50 (1M 토큰당). 출처는 `results/carttrace_protocol_ext_20261122/part2/RUN_PLAN_rev6.json`(2026-11-21 확인).
- **호출 가능 여부: 미확인.** 현재 `OPENAI_API_KEY`가 설정돼 있지 않다. 연구자가 환경 변수를 설정한 뒤 `GET /v1/models`(무과금)로 `gpt-6-luna`가 있는지 확인하고 나서 실행한다.
- **dry-run 실측(네트워크 없음, 실제 프롬프트 크기)**
  - 1단계 + plain 입력 추정: R1 31.2만, R3 16.5만, R2 66.3만, G1 12.0만 토큰 = 약 126만 토큰
  - 2단계(사용자 턴당 최대 1회)를 더하면 입력은 약 270만 토큰
  - 호출 수: 약 4,800회(1단계 + plain 2,733회 + 2단계 최대 2,097회)
- **추정 비용**
  - 입력 약 $0.27
  - 출력: 호출당 평균 300토큰(추론 포함)을 가정하면 약 $0.72. 합계 약 **$1.0**
  - 최악(모든 호출이 출력 2,000토큰): 약 **$5.1**
- **실행 상한: $15.** 하네스가 매 호출 전에 최악 비용으로 확인하고, 넘으면 멈춘다. 모든 호출은 `results/e_m1_20261126/ledger.jsonl`에 기록한다(요청 sha256, 사용량, 비용, 지연. 키는 기록하지 않음).

## 6. 절차

1. 연구자가 `OPENAI_API_KEY`를 설정한다 → 모델 목록 확인(무과금)
2. 파일럿 10여정 → 파싱 실패율과 비용 보고. 파일럿으로 바꿀 수 있는 것은 출력 파싱뿐이다.
3. 본 실행: R1 → R3 → R2 → G1 순서
4. 분석: 같은 행 파일에서 팔별 지표를 낸다. 여정 단위 Wilson 95% 구간을 쓴다.

## 7. 전체 평가 계획 안에서의 위치

- A-VIP·Standing과의 비교는 WhisperBench에서 무과금으로 이미 했다(X1, `results/whisperbench_e2_20261126`). Standing 규칙(재구현) 팔은 그래프에서 같은 기록으로 계산한다.
- E-M1은 그 위에서 M1(맥락 검증)의 효과를 실제 대화로 재는 핵심 실험이다.

## 8. 한계

- 쇼핑객은 시뮬레이터다. 실제 사용자 수정(완화·철회)은 G1(생성)에만 있다.
- 결제 검사는 기록된 장바구니에 대한 오프라인 판정이다. 에이전트 행동의 변화는 재지 않는다.
- 정답 사양은 CartTrace 판정표의 한계를 물려받는다.
- 브랜드와 묶음 품목명은 카탈로그 이름과 사용자 표현이 달라 규칙 근거 찾기가 약하다(누락 검사 결과 참고).

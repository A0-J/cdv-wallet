# M1 v2 설계 진단 (2026-11-26, 무과금, 규칙 변경 없음)

- 스크립트: `eval/m1_v2/diagnose.py` → `diagnostics.json`
- 모델 호출 0. PLAN_v3 결과 파일은 읽기만 했다.
- D1·D4·D5는 E-M1 test 행(이미 본 데이터)에 대한 **서술 진단**이다. 설계의 수치 기준은 여기서 정하지 않고 validation에서 정한다(`docs/M1_V2_DESIGN.md` 6절).
- D2·D3(validation)은 모델 출력 없이 원본 대화·도구 기록만 썼다.

## D1. product_type에 무엇이 들어 있나 (요청 1) — E-M1 FnCTOD 상태 1,364개 값

| 값의 종류 | 수 |
|---|---:|
| 일반 종류 (≤3단어, 예: "journal", "boots") | 555 |
| 구체 상품명 (에이전트가 본 카탈로그 제목과 60% 이상 겹침) | 483 |
| 조건·후보 혼합 ("A or B", "cheapest of: …", "… or a similar alternative if unavailable") | 218 |
| 긴 설명 (카탈로그와 불일치) | 108 |

- **확인됨: 한 필드에 상품 종류, 구체 상품명, 후보 목록, 대체 조건이 섞여 있다.**
- M1(규칙)이 `확인대기:ptype`을 낸 변경 268건의 종류
  - 일반 → 구체 상품명 46, 후보 혼합 → 구체 상품명 42: **후보 중 하나를 고른 것(선택)** 또는 구체화
  - 구체 → 다른 구체 53: 상품 선택 변경
  - 구체 → 후보 혼합 30, 일반 → 후보 혼합 6: 대체 조건이 상품 이름 칸에 들어감
  - 나머지 91: 표현만 바뀐 것 등
- 판단(AI 1차): ptype 확인 요청의 대부분은 구매 제약 변경이 아니라 **상품 선택**이다. 그러나 구체 → 다른 구체(53)에는 실제 상품 변경 위반이 섞일 수 있어 일괄 제거하면 안 된다(요청 6).

## D2. 참조 표현을 에이전트 후보와 연결할 수 있나 (요청 4) — validation 4,015여정, 모델 출력 없음

| 항목 | 수 | 비율 |
|---|---:|---:|
| 쇼핑객 턴 | 11,353 | |
| 참조 표현이 있는 턴 ("option 2", "the second one", "that one" …) | 1,083 | 9.5% |
| 직전 에이전트 메시지에 번호·글머리 목록이 있음 | 856 | 참조 턴의 79.0% |
| 번호·서수로 목록 항목을 특정함 | 788 | 72.8% |
| 그 항목을 에이전트가 받은 검색 결과의 상품(SKU)과 제목으로 연결함(겹침 ≥ 0.5) | 505 | 46.6% |
| 지시어("that one")인데 후보가 하나뿐 | 100 | 9.2% |
| 지시어인데 후보가 여럿(모호) | 194 | 17.9% |

- **가능하다. 다만 상품 수준 연결은 절반 정도**이고, 변형(색·사이즈) 수준 연결과 지시어 해석은 더 다듬어야 한다.
- 근거로 쓰는 것은 에이전트가 화면에 보인 후보와 검색 도구 결과(환경 사실)뿐이다. 판매자 문장은 참조 대상을 찾는 데만 쓰고, 구매 권한을 바꾸는 근거로는 쓰지 않는다.

## D3. M2a가 못 보는 위반 (요청 7)

| 데이터 | 위반 여정 | 장바구니 상품이 숨은 사양의 허용 상품(witnesses) 밖 | 허용 상품 안인데 위반 |
|---|---:|---:|---:|
| validation 전체 | 918 | 317 (34.5%) | 601 |
| E-M1 R1 | 48 | 16 | 32 |
| E-M1 R3 | 20 | 17 | 3 |
| E-M1 R2 | 73 | 57 | 16 |

- 장바구니 상품이 만족하지 못한 조건의 종류(validation, 위반 여정): 상품 종류(`kind`) 175, 예산(`max_price`) 107, 속성 일치(`eq`, 색·사이즈 등) 77, 대체 선호(`prefer`) 72, 묶음(`all_of`) 37, 최저가(`cheapest`) 22, 언급(`mentions`) 16, 택일(`one_of`) 7 …
- **M2a는 예산·수량·묶음 개수·브랜드만 본다.** 상품 종류, 속성, 대체 선호, 최저가, 택일은 상품(SKU) 수준 선택 상태가 있어야 검사할 수 있다.
- 전체 게이트(`cdv/gate.py`)의 Scope에는 허용 상품 목록(`cart_ids`), 필수 속성(`required_features`), 판매자, 총액, 브랜드, 수량 상한이 있지만, **장부를 Scope로 바꾸는 코드가 없고** 브랜드 제외, 묶음 전부 포함, 정확한 수량, 수령 방식·기한 칸이 없다.
- 남은 601건 등 "허용 상품 안인데 위반"은 결제 외 단계(정보 전달, 확인 등)의 문제일 수 있다. 원인은 아직 나누지 않았다.

## D4. 숨은 사양에 없다는 이유로 '부당'으로 센 조건 (요청 8) — E-M1 FnCTOD 최종 상태

| 분류 | 사용자 발화에서 근거 찾음(규칙 또는 NLI) | 못 찾음 |
|---|---:|---:|
| 숨은 사양에 아예 없음 | **76** | 84 |
| 숨은 사양에 있으나 출처가 `default`(사용자가 말하지 않은 기본값) | **62** | 64 |
| 값이 다름 | 1 | 12 |
| 합계 299 | **139 (46%)** | 160 |

- 대표 유형: 상품명 속 브랜드("I'd like the **AmazonBasics** Gel Ink Pens …") → brand_in 73건. 숨은 사양에는 브랜드 조건이 없다.
- **주의(규칙의 근거 찾기 정밀도 문제):** 수량 1의 '근거'가 주소의 숫자("1 Maple Way")나 "option 1"에서 잡힌 예가 있다. 수량 규칙이 숫자만 보면 근거로 잡는다. 따라서 139건은 상한 추정이다.
- 결론: PLAN_v3의 '부당 조건 탐지율'은 숨은 사양을 기준으로 해서, 사용자가 실제로 말한 조건을 거부해도 '탐지'로 센다. 기준을 사용자 발화 중심으로 다시 정해야 한다.

## D5. 결제 요청 뒤 발화가 판정에 들어갔나 (요청 9)

- **들어갔다.** PLAN_v3 하네스는 대화 전체의 마지막 상태와 전체 발화로 최종 장바구니를 판정했다. 결제 요청 뒤 쇼핑객의 승인·거절 발화("That isn't what I asked for. Don't place the order.")도 포함됐다. 일반 LLM 팔은 대화 전체를 한 번에 읽으므로 같다.
- 결제 동의 요청 시점(지갑 확인 메시지 또는 checkout mandate 요청)을 찾을 수 있는 여정

| 세트 | 결제 요청 시점 있음 | 그 뒤 쇼핑객 발화가 있는 여정 | 장바구니만 만들고 끝난 여정(결제 단계 없음) |
|---|---:|---:|---:|
| R1 | 97/200 | 93 | 103 |
| R3 | 47/100 | 43 | 53 |
| R2 | 96/96 | 87 | 0 |

- 저장된 FnCTOD 턴별 상태를 결제 요청 직전까지 자르고 같은 규칙으로 다시 판정(오프라인, 무과금)했을 때 판정이 바뀐 여정: R1 규칙 9 / NLI 14 (97 중), R3 11 / 10 (47 중), **R2 25 / 26 (96 중)**, FnCTOD 단독 R2 10.
- R2는 "고르기 뒤 거절"을 선택 기준으로 삼았으므로 선택 자체는 문제가 아니지만, 검증기가 거절 발화를 본 것은 누설이다. **PLAN_v3의 R2 수치는 이 누설을 포함한다.**

# M1 v2 설계안: 구매 제약 상태와 상품 선택 상태의 분리 (검토용, 구현 전)

- 작성: 2026-11-26. **상태: 설계 검토 대기. 규칙 변경·구현·유료 실행 없음.**
- 근거: PLAN_v3 1차 결과(`results/e_m1_20261126/`, 보존)와 무과금 진단(`results/m1_v2_design_20261126/README.md`, D1–D5).
- 전체 구조는 그대로 둔다: 턴마다 M1 → 검증된 조건으로 Mandate 발급 → 결제 시점 M2. 바꾸는 것은 M1의 상태 모델과 재확인 정책, 그리고 M1 → Mandate → M2 연결이다.
- 목표(연구자 지시): 사용자 의도의 정상적인 변화는 반영하고, 근거 없는 구매 조건 변경과 누락은 막는다. 기존 조건을 무조건 유지하거나 모든 상품 변경에 확인을 요청하는 것이 목표가 아니다.

## 1. 두 상태

| | 구매 제약 상태 C (Constraint State) | 상품 선택 상태 S (Selection State) |
|---|---|---|
| 뜻 | 사용자가 위임한 **권한 범위**. 결제가 넘으면 안 되는 경계 | 그 범위 안에서 **지금 고른 상품** |
| 항목 | 예산, 수량, 묶음(반드시 포함할 품목), 브랜드 포함·제외, 기한, 수령 방식, 대체 허용과 범위, 사용자가 말한 속성(색·사이즈 등), 사용자가 지명한 목표 상품(대체 불허일 때) | 후보 참조(목록 번호·이름), 연결된 상품 ID·변형 ID, 제시 시점, 출처(사용자 지명 / 사용자 고름 / 에이전트 제안) |
| 변경 근거 | 사용자 발화만. 넓히는 변경은 명시적 단서 필요(V-C 그대로) | 사용자 발화 + 에이전트가 보인 후보·도구 결과(환경 사실) |
| 판매자 정보 | 근거로 쓰지 않음 | 참조 대상과 상품 사실(가격·재고·속성)로만 씀 |
| 결제 시 검사 | Mandate Scope로 옮겨 M2가 검사 | 장바구니 상품 ⊆ 선택 상태(허용 상품 목록) |

- 현재 `product_type`은 쪼갠다(D1: 종류 555, 구체 상품명 483, 후보·대체 조건 혼합 218).
  - 일반 종류("boots") → C의 약한 항목. 확인 요청 대상 아님. 근거 찾기 보조에만 씀.
  - 구체 상품명·후보 → S.
  - "or a similar alternative if unavailable" 같은 문구 → C의 대체 정책(V-S).
  - 사용자가 처음부터 특정 상품을 지명하고 대체를 허락하지 않았으면 → C의 목표 상품.
- FnCTOD 함수 스키마는 바꾸지 않는 안(A)을 기본으로 한다. S는 대화의 에이전트 목록과 도구 결과에서 결정적으로 만든다. 그래야 저장된 추출 결과를 재사용할 수 있다(8절). 스키마에 `select_product` 함수를 더하는 안(B)은 A가 validation에서 부족할 때만 검토한다.

## 2. 변경 분류와 처리

| 변경 | 예 | 처리 |
|---|---|---|
| S 변경, 고른 후보가 C를 만족 | "I'll go with option 2" → 2번이 예산·브랜드·묶음 안 | **확인 없이 반영**(기록만) |
| S 변경, 고른 후보가 C를 벗어남 | 2번이 예산 초과, 제외 브랜드, 묶음 품목 빠짐, 대체 불허인데 다른 상품 | C를 넓히는 변경으로 취급 → 사용자 명시 단서가 있으면 C 변경으로 반영, 없으면 미해결(3절) |
| S 변경, 참조를 후보에 연결 못 함 | 후보가 여럿인데 "that one" | 미해결(3절) |
| S 변경 제안이 에이전트·판매자에게서만 나옴 | 에이전트가 고르고 사용자는 응답 없음 | 반영하지 않음. 단일 후보 제시에 사용자가 "sounds good"이면 그 후보를 고른 것으로 해석 |
| C 좁힘 | 예산 인하 | 사용자 근거 있으면 반영 |
| C 넓힘 | 예산 인상, 묶음 품목 제외, 대체 허용 | 명시적 단서 필요(현행 V-C) |
| C 충돌 | 브랜드 포함·제외 동시 | 미해결(현행 V-X) |

### 근거 미발견과 비사용자 출처 분리 (리뷰 지적, D4)

- `NON_USER_SOURCE`: 그 값이 에이전트·판매자·도구 문장에만 있고 사용자 발화에는 없음(예: 장바구니 총액 $135.58을 예산으로 넣음) → 거부.
- `NOT_FOUND`: 어느 쪽에서도 근거를 못 찾음(추출기가 바꿔 말함) → 버리지 않고 '미검증'으로 유지, NLI로 다시 확인, 그래도 없으면 미해결 목록에 남김(조용히 버리지 않음).
- 기본 구성은 규칙 + NLI로 한다.
- 수량 규칙의 근거 찾기를 수량 문맥이 있을 때로 좁힌다(주소 숫자, "option 1"을 근거로 잡는 문제, D4).

## 3. 선택적 재확인 (요청 5)

모든 미해결 항목이 결제를 막는 현행 방식 대신, **결제 요청 시점 t에서 미해결 항목 u가 그 결제의 적법성을 바꾸는지**로 정한다.

1. t 이전 발화만으로 C, S, 미해결 목록 U를 만든다.
2. 각 u ∈ U에 대해 'u를 받아들인 C/S'와 'u를 받아들이지 않은 C/S'로 같은 장바구니를 M2로 두 번 검사한다.
3. 두 판정이 같으면 u는 이 결제와 무관 → 묻지 않는다(기록만, Mandate에는 미검증 표시).
4. 다르면 → 이 결제에 한해 CLARIFY(무엇을 묻는지 u로 특정).
5. 누락 경보도 같다: 발화에서 찾은 누락 조건을 장바구니가 어기면 CLARIFY, 어기지 않으면 기록만.

- 이것은 기존 설계 문서의 "결정이 그 변경에 기댈 때만 묻는다"를 구현하는 것이다.
- **상품 변경 확인을 없애지 않는다(요청 6).** 상품 변경은 S와 M2의 '장바구니 상품 ⊆ 선택 상태' 검사로 잡는다. 사용자가 고르지 않은 상품이 장바구니에 있으면 그것이 결정에 직접 영향을 주므로 묻거나 막는다.

## 4. 참조 해석 (요청 4)

- 후보 등록부: 에이전트 메시지의 번호·글머리 목록 항목, 검색·조회 도구 결과의 상품(ID, 제목, 가격, 변형).
- 해석 순서: 번호·서수 → 목록 항목 → 제목 겹침으로 상품 ID / 이름 언급 → 제목 겹침 / 지시어 → 후보가 하나면 그것, 여럿이면 미해결.
- validation 실측(D2): 참조 턴의 72.8%가 목록 항목으로 특정되고, 46.6%가 상품 ID까지 연결된다. 변형(색·사이즈) 연결은 아직 없다.
- 판매자·도구 정보는 "그 후보가 C를 만족하는가"를 판단하는 사실로만 쓴다. C를 바꾸는 근거로는 쓰지 않는다(E2 원칙과 같음).

## 5. 시간 순서와 M2 연결 (요청 7, 9)

- **판정 시점:** 결제 동의 요청(지갑 확인 메시지, checkout mandate 요청) 또는 장바구니 전달(결제 단계가 없는 여정) 직전. 그 뒤 발화는 판정에 쓰지 않는다. 일반 LLM 팔도 그 시점까지 자른 대화로 다시 추출한다.
- **장부 → Mandate 변환을 새로 만든다.** 필요한 Scope 확장:

| C/S 항목 | 현재 Scope | 필요한 변경 |
|---|---|---|
| 예산 | `max_total` | 그대로 |
| 수량 | `max_quantity`(상한) | 정확한 수량 칸 추가 |
| 브랜드 포함 | `brands` | 그대로 |
| 브랜드 제외 | 없음 | `brands_excluded` 추가 |
| 묶음 | 없음(`cart_ids`는 허용 목록) | `required_all` 추가 |
| 선택 상품 | `cart_ids` | S의 상품·변형 ID로 채움 |
| 사용자 속성 | `required_features` | C의 속성으로 채움 |
| 수령 방식·기한 | 없음 | 결제 옵션 검사 칸 추가 |

- 통합 평가는 M2a가 아니라 이 전체 게이트(서명·A-VIP 결합·Scope·조건부 절)로 한다. 그래야 결합 효과를 주장할 수 있다.

## 7. 평가 지표 정리

- 확인 요청(CLARIFY)과 거부(DENY)를 따로 보고한다.
- 부당 조건의 기준을 **사용자 발화**로 바꾼다. 숨은 사양은 보조 기준이다.
  - 기준표: validation 표본에서 AI 1차 표지(조건마다 '사용자가 말함 / 말하지 않음 / 다른 값') → 연구자 2차 검토.
- G1에 **기존 조건 보존율**(이전 장부 조건이 근거 없이 사라지지 않은 비율)을 더한다.
- 선별성: 위반 여정 차단율 − 정상 여정 차단율(CLARIFY, DENY 각각).
- 상품 변경 위반: 장바구니 상품이 사용자가 고른 상품 밖인 여정의 탐지율.

## 8. 기존 API 응답으로 오프라인 재평가 (요청 10)

- **가능하다(FnCTOD 세 팔).** 행 파일에 턴별 FnCTOD 상태가, `ledger.jsonl`에 요청 sha256별 원 출력이 있다. 1–7절의 변경은 모두 검증 단계이므로 저장된 추출 결과 위에서 다시 돌릴 수 있다. 결제 시점 절단도 그 시점까지의 턴 상태만 쓰면 된다(FnCTOD 프롬프트는 턴마다 그 턴까지의 대화라서 같음).
- **일반 LLM 팔은 다시 호출해야 한다.** 대화 전체를 한 번에 읽었기 때문에, 결제 시점까지 자르면 프롬프트가 달라진다. (R1+R3+R2 약 400회, 약 $0.03 추정)
- **단, 이 재평가를 test_cross_store에서 하는 것은 설계 확정용이 아니다.** 이미 본 데이터라 사후 비교로만 쓸 수 있다. 설계는 validation에서 정한다.
- FnCTOD 스키마를 바꾸는 안(B)을 택하면 저장된 추출을 재사용할 수 없다.

## 9. validation 평가 계획 (설계 확정용)

- validation에는 FnCTOD 출력이 10여정(파일럿)뿐이다. 개발용 추출이 필요하다(유료, 승인 필요).

| 세트 | 수 | 쓰임 | 추정 비용 |
|---|---:|---|---:|
| V1 일반 | 200 | C/S 분리, 재확인 정책 | 약 $0.15 |
| V3 대체 + 품절 | 100 (validation에 290 가능) | 대체 범위, 상품 변경 | 약 $0.08 |
| V2 품절 → 고르기 → 거절 | validation에서 정규식 선택 | 선택 변경 | 약 $0.1 |
| G1 dev | 260 (이미 있음) | 템플릿 기능, 보존율 | 약 $0.1 |
| 참조 해석·사용자 발화 기준표 | V1·V2 중 100여정 | AI 1차 표지 → 연구자 2차 | $0 |

- 정할 것: product_type 분할 규칙, 참조 해석 문턱(제목 겹침), 결정 관련성 판정, NOT_FOUND 처리, 수량 근거 문맥.
- 정한 뒤 코드 해시와 함께 새 계획(PLAN_v4)으로 고정하고 sha256을 보고한다.

## 10. 최종 평가 데이터 (미사용 데이터 확보 가능성)

| 후보 | 상태 | R1형 가능 | R3형(품절) 가능 | 판단 |
|---|---|---:|---:|---|
| test_cross_store | PLAN_v3에서 씀 | – | – | 새 독립 test 아님 |
| **test_cross_template** | M1 개발·평가에 안 씀. 다만 2026-11-23 이전 연구 단계에서 집계 수준으로 확인함(`private/docs/PLAN_EXP3_GENERALIZATION_20261124.md`), 노출 기록 174여정 | 7,872 (노출·사용 제외) | **0** (품절 결함 없음) | R1·R2형 최종 평가 후보. "M1 개발에 쓰지 않은 분할"로 표기 |
| train | M1에는 R2 선택 일부만. 이전 연구 실험 3이 일부 과제를 씀 | 67,225 | 5,359 | R3형 최종 평가는 train에서 떼어 둔 표본으로(실험 3 과제 제외) |
| G1 eval | PLAN_v3에서 씀 | | | 새 G1 eval을 test_cross_template 기반으로 다시 생성 |

- 최종 평가 표본 ID는 설계 확정 전에 미리 뽑아 sha256으로 봉인하고, 설계가 끝날 때까지 열지 않는다.
- 최종 평가 추정 비용: R1형 300 + R2형 100 + R3형 100 + G1 260 ≈ $0.6–1.0 (gpt-6-luna, PLAN_v3 실측 기준).
- 엄밀히 '한 번도 안 본 데이터'는 없다. 논문에는 "M1 개발에 쓰지 않은 분할 + 표본 봉인"으로 적는 것이 정확하다.

## 11. 연구자 결정이 필요한 것

1. FnCTOD 스키마 유지(안 A, 결정적 선택 상태) vs 선택 함수 추가(안 B)
2. validation 개발용 추출 실행 승인(약 $0.4)
3. 최종 평가 데이터: test_cross_template(R1·R2형) + train 떼어 둔 표본(R3형) + 새 G1
4. 사용자 발화 기준표의 범위(표본 수)와 연구자 2차 검토 시간
5. 전체 게이트 통합 평가를 이번 학위논문 범위에 넣을지(Scope 확장 필요)
